# Part I. CAN 결합 실험

## 1. 이 실험이 무엇인가

우리 모델은 진동·전류 신호를 STFT로 변환한 PNG에서 뽑은 특징을 쓴다. 최종 구성은 87채널이다.

```
3개 센서(Current_U, Vib_Motor, Vib_TM)의 PNG
    ↓
센서별 기본 특징 4개 + RPM 1개 + 절대 주파수축 특징 12개 + 차수축 특징 12개 = 29개
    ↓
29 × 3센서 = 87채널 × 2000프레임
    ↓
MiniRocket (커널 9,996개) → LogisticRegression → 5개 클래스
```

이와 별개로 CAN 참조데이터(Other 폴더)에는 모터 CSV 183,600개가 있고, 각 파일에서 5개 신호 × 5개 통계 = **25개 요약 특징**을 만들어 뒀다.

| 신호 | 통계 |
| --- | --- |
| torque_ref (목표 토크) | 평균, 표준편차, 최솟값, 최댓값, 고유값 수 |
| torque_act (실제 토크) | 〃 |
| rpm (회전속도) | 〃 |
| temp_inv (인버터 온도) | 〃 |
| temp_motor (모터 온도) | 〃 |

**이 실험은 그 25개 특징을 87채널 모델에 실제로 붙여서 성능이 오르는지 측정한 것이다.**

CAN 전처리 과정 자체는 별도 문서 [참조데이터_전처리_정리.md](https://app.notion.com/p/%EC%B0%B8%EC%A1%B0%EB%8D%B0%EC%9D%B4%ED%84%B0_%EC%A0%84%EC%B2%98%EB%A6%AC_%EC%A0%95%EB%A6%AC.md) 참조.

## 2. 왜 이 실험을 했는가

### 2-1. 미검증 상태로 남아 있었다

CAN 데이터 분석은 전처리와 단독 분류 실험까지 끝나 있었지만, **우리 모델에 결합하는 단계는 하지 않은 상태**였다. 그래서 발표에서 "활용 가능한 특징을 구축했다"까지만 말할 수 있고 "그래서 성능이 올랐다/안 올랐다"는 말할 수 없었다.

### 2-2. 단독 실험 결과가 기대를 갖게 했다

25개 특징만으로 RandomForest를 학습했을 때 F1이 0.5 수준으로, 5클래스 무작위(0.2)보다 훨씬 높았다. 신호에 판별 정보가 들어 있다는 뜻이다. 다만 **단독 판별력과 결합 이득은 다른 문제**다. 기존 이미지 특징이 이미 같은 정보를 담고 있다면 결합해도 늘지 않는다. 그 구분을 짓는 것이 이 실험의 목적이다.

### 2-3. 세 가지 미확인 신호가 있었다

| 신호 | 기존 모델에서의 상태 |
| --- | --- |
| RPM | 이미 사용 중 (보조 입력 + 차수축 정규화) |
| 인버터 온도 | A3 실험에서 추가했다가 성능 하락으로 기각 (0.881 → 0.873) |
| **모터 온도** | 한 번도 넣어본 적 없음 |
| **토크 2종** | 한 번도 넣어본 적 없음 |
| **변동 통계(표준편차·최소·최대·고유값 수)** | 한 번도 넣어본 적 없음 |

기존에 "온도를 넣었다가 뺐다"는 실험은 CAN 분석 결과 **인버터 온도**였음이 확인됐다. 모터 온도는 별개 신호이므로 다시 시험할 가치가 있었다.

## 3. 어떻게 결합했는가

### 3-1. 결합 위치

CAN 특징은 **MiniRocket 출력 뒤에 한 번만** 붙인다.

```
87채널 × 2000프레임 → MiniRocket → 9,996차원 특징 벡터
                                        ↓
                          [9,996차원] + [CAN 특징 N개]
                                        ↓
                            StandardScaler → LogisticRegression
```

CAN 값을 2000프레임에 반복해 채널로 넣는 방식은 쓰지 않았다. CAN 요약값은 PNG 한 장 전체에 대한 상수라서, 시계열 채널로 넣으면 MiniRocket의 합성곱 비용만 늘고 정보는 같기 때문이다.

### 3-2. 비교한 5개 구성

| 이름 | 추가 특징 | 차원 |
| --- | --- | --- |
| `baseline87` | 없음 (기준) | 9,996 |
| `motor_temp` | 모터 온도 평균 | 9,997 |
| `torque_stats` | 실제 토크 평균·표준편차 | 9,998 |
| `rpm_dynamics` | RPM 표준편차·최솟값·최댓값·고유값 수 | 10,000 |
| `all25` | CAN 전체 25개 | 10,021 |

구성을 넷으로 나눈 이유는 **"CAN 중 어느 신호가 기여하는가"**를 분리하기 위해서다. all25만 돌리면 개선이 있어도 원인을 모른다.

### 3-3. 진단용 CAN 단독 모델

같은 표본·같은 폴드에서 CAN 특징만으로 분류하는 모델도 함께 학습했다(LR 4종 + RandomForest 25특징 1종). 결합 이득이 없을 때 **"CAN에 정보가 없어서"인지 "정보는 있는데 이미 이미지가 담고 있어서"인지** 구분하기 위한 장치다.

## 4. 데이터를 어떻게 연결했는가

### 4-1. 연결 키

`vehicle + timestamp + seq + zsplit + PNG 번호`

PNG 조각 하나당 CAN CSV 한 개가 대응한다. 라벨(고장 클래스)은 **연결한 뒤 일치 검사에만** 썼고 학습 특징에는 넣지 않았다. 파일명·차종명·timestamp도 마찬가지로 특징에서 제외했다.

CV 그룹은 차종 내 `timestamp`다.

### 4-2. 기존 코드에서 찾은 버그

기존 데이터 연결 코드는 키에서 **seq(순번)를 빠뜨리고** 있었다. 같은 시각·같은 zsplit 안에 순번이 여러 개 있는데 이를 구분하지 않아 일부 파일이 덮어써지고 있었다.

> 감사 결과: 센서 파일 38,160개 중 **13,869개(36.3%)**가 옛 키 기준으로 중복 — 즉 덮어쓰기 대상이었다.
> 

이번 파이프라인은 seq를 키에 포함했다. **이 수정 때문에 기존 0.973과 직접 비교할 수 없게 되어, 기준 모델을 새 조건에서 다시 측정했다.**

### 4-3. 연결 검증 결과

| 검사 | 결과 |
| --- | --- |
| 전체 PNG 구간 | 146,880개 |
| CAN 연결 성공 | 146,880개 (미연결 0) |
| 세그먼트 | 12,720개, 전부 3센서 완비 |
| CAN CSV | 183,600개 |
| 센서 간 PNG 목록·행 수·라벨 일치 | 통과 |
| 라벨링 캐시 RPM vs CAN 평균 RPM | 전부 0.02 RPM 이내 일치 |
| **특징데이터 RPM vs CAN 평균 RPM** | **최대 오차 0.000** (3개 차종 모두) |
| CAN 값에 NaN/무한대 | 없음 |

PNG 번호가 중간에 건너뛰는 경우(전체 30,380곳)도 실제 파일 목록 순서로 연결해 CAN 값이 한 칸씩 밀리지 않도록 처리했다.

> CAN 통계는 PNG 전체 구간의 값이다. 부분 구간만 관측한 조기 진단 성능을 뜻하지 않는다.
> 

## 5. 검증을 어떻게 설계했는가

### 5-1. 교차검증

- 차종별로 따로 학습·평가 (IONIQ / KONA / NIRO)
- `timestamp`를 그룹으로 하는 StratifiedGroupKFold 3분할, seed=42
- 같은 주행(timestamp)이 학습과 검증에 동시에 들어가지 않는지 **매 폴드 실행 시점에 재확인**
- 각 샘플은 검증에 정확히 한 번만 등장(OOF 커버리지 검사 통과)

### 5-2. 전처리 누수 차단

기존 학습 코드는 채널 정규화와 MiniRocket을 **교차검증 이전에 전체 데이터로** 맞추고 있었다. 검증 데이터가 전처리 학습에 참여하는 구조다.

이번에는 폴드마다 **학습 데이터만으로** 채널 평균·표준편차, MiniRocket, LR 스케일러를 fit했다. 그래서 기준 모델도 같은 조건으로 다시 측정했다.

참고: [학습 데이터에서만 전처리를 fit하는 원칙](https://scikit-learn.org/0.24/common_pitfalls.html) · [다변량 MiniRocket](https://www.sktime.net/docs/api-reference/sktimetransformationsrocketminirocketmultivariate/)

### 7-1. 왜 이득이 없었는가

CAN 단독 F1 0.53과 결합 이득 0의 조합이 답을 준다. **정보가 없어서가 아니라, 이미 이미지 특징이 같은 정보를 담고 있어서다.**

가장 유력한 경로는 RPM이다. RPM은 이미 두 번 쓰이고 있다.

1. 87채널의 보조 입력으로 직접 들어간다
2. 차수축(order axis) 특징 12개를 만들 때 주파수축 정규화 기준으로 쓰인다

CAN 단독 구성 중 RPM 변동 통계가 가장 강하고(0.318) 온도·토크는 0.2 안팎인데, 이는 **CAN의 판별력 상당 부분이 회전속도 즉 주행 조건에서 온다**는 것을 시사한다. 그리고 그 조건 정보는 이미 모델 안에 있다.

같은 맥락에서, 온도와 토크의 기여가 낮은 것은 A3 실험(인버터 온도 추가 시 0.881→0.873 하락)과도 방향이 일치한다. **모터 온도는 인버터 온도와 다른 신호지만, 결과적으로는 마찬가지로 기여하지 못했다.**

`모터_특징추출_v2.py`의 `to_order_axis()`는 `REF_RPM = 9100`을 쓴다. 차수 o가 가리키는 원본 bin이 `o × (H-1) × (rpm/9100)`이므로, **데이터 최대 RPM 8,579 < 9,100이면 잘림(NaN)이 구조적으로 발생하지 않는다.** 오히려 고RPM일수록 원본 주파수축을 넓게 사용해 차수 해상도가 좋아진다.

즉 "고RPM에서 신호가 화면 밖으로 나간다"는 설명은 배제된다.

## 12. 해석

감자(DEMAG)는 영구자석의 자속이 줄어든 상태다. 같은 토크를 내려면 더 많은 전류가 필요하다.

- **정속·저부하 순항**에서는 전류·진동 패턴이 정상과 거의 같다. 부하가 작으면 자속 부족이 드러날 여지가 없다.
- **가감속·부하 변동** 중에는 제어기가 보상 동작을 하고, 그 과정에서 정상 대비 차이가 스펙트로그램에 나타난다.

스펙트로그램 관점에서도 설명이 된다. RPM이 변하면 회전 성분은 주파수가 따라 움직이고 고정 성분(공진·배경 잡음)은 그대로 있다. 이 **움직임 자체가 회전 기인 성분을 분리해 주는 단서**다. 정속에서는 모든 성분이 수평선이라 구분할 근거가 줄어든다.

> 주의: 위 해석은 데이터와 정합적이지만 물리적으로 검증한 것은 아니다. 확정하려면 동일 세션의 정적·동적 구간 스펙트로그램을 직접 대조해야 한다.
> 

### 모델은 "확신하며" 틀린다

고RPM 오류의 47.6%가 확률 0.9 초과다(전체 오류 49.1%와 비슷). 즉 **확률 임계값만으로는 이 오류를 걸러낼 수 없다.** 조건 기반 게이팅이 필요한 이유다.

## 13. 활용 — 동적 구간에서만 진단하기

RPM과 토크는 이미 CAN에서 실시간으로 들어온다. 창(window) 안의 표준편차를 계산해 **정적 구간의 진단 결과를 버리는 것**은 추가 학습도, 추가 센서도 필요 없다.

### 클래스별 재현율 (차종 평균)

클래스 혼합 변화의 영향을 받지 않는 지표다.

### 13-1. 실제 운용 흐름

게이팅 변수는 **`torque_act_std` 하나**다. 평균이 아니라 **표준편차**라는 점이 핵심이다. "토크가 얼마나 큰가"가 아니라 **"창 안에서 토크가 얼마나 출렁였는가"**를 본다.

계산 범위는 명확하다. 참조 CSV 1개 ↔ PNG 조각 1개가 **정확히 1:1**이다(146,880 : 146,880 확인). 모델이 한 번 판정하는 바로 그 구간의 토크 표준편차다.

```
CAN 버스 (차량에서 상시 수신)
    │
    ├─ torque_act 스트림 ──────┐
    │                          │
    └─ 진동·전류 센서          │
           │                   │
           ▼                   ▼
    한 구간 수집          같은 구간의 토크 표준편차 계산
           │                   │
           │              std ≥ 임계값?
           │                   │
           │         ┌─── 아니오 ──→ 판정하지 않고 폐기, 다음 구간 대기
           │         │
           │        예
           ▼         ▼
    STFT → PNG → 특징 → MiniRocket → LR → 5클래스 판정
```

#### 임계값은 차종별로 다르다

홀드아웃에서 DEV 세션 분포로만 정한 값이다(§16-2-1).

| 차종 | p50 (커버리지 약 50%) | p75 (약 25%) |
| --- | --- | --- |
| IONIQ | 17.74 | 29.73 |
| KONA | 14.52 | 27.49 |
| NIRO | 12.41 | 24.36 |

차종마다 통상 운전 토크 수준이 다르므로 **절대값을 공유하면 안 된다.** 차종별로 개발 데이터에서 분위수를 잡는다.

#### 순서가 중요하다

게이트는 **모델을 돌리기 전에** 계산된다. 토크 표준편차는 덧셈 몇 번이면 끝나고 모델은 청크당 35.4ms가 든다.

> **약 46%의 구간에서 STFT·MiniRocket을 아예 돌리지 않아도 된다.** 라즈베리파이 이식 시 정확도와 연산량을 동시에 얻는다.
> 

단, 이번 실험은 전부 돌린 뒤 사후에 걸러낸 것이다. 결과는 같지만 배포 때 순서를 바꾸면 연산이 절약된다는 것이 설계상의 함의다.

#### 왜 모델 확률로 거르면 안 되나

"확률이 낮으면 판정 보류"가 더 간단해 보이지만 안 된다. **모델이 확신하며 틀리기 때문이다** — 오류의 약 49%가 확률 0.9를 넘는다(§12).

반면 토크 변동은 **모델 밖의 독립적인 정보**라서, 모델이 무엇을 착각하든 상관없이 "지금은 판단하기 어려운 상황"을 알려 준다.

#### "판정하지 않음"은 실패가 아니다

차량 진단은 연속 감시다. 한 구간을 건너뛰어도 다음 구간이 계속 온다. 가속·감속·부하 변동은 일반 주행에서 흔하다. 세션의 98.5%에 적격 구간이 있고 중앙값으로 56.9%가 적격이다.

## 14. 반드시 함께 말해야 할 주의사항

### 이것은 모델 개선이 아니다

성능이 오른 것이 아니라 **쉬운 구간만 골라 평가한 것**이다. 100% 커버리지의 0.974와 50% 커버리지의 수치를 나란히 놓고 "개선"이라고 말하면 안 된다. 정확한 표현은 **"선택적 진단(selective prediction)"**이다.

### macro-F1 수치는 클래스 혼합이 바뀌어 직접 비교가 어렵다

torque_std 중앙값 게이트가 각 클래스를 남기는 비율:

| 클래스 | 잔존율 | 중앙 torque_act_std |
| --- | --- | --- |
| REDUC | **80.6%** | 30.21 |
| ECC20 | 46.2% | 13.54 |
| ECC10 | 44.4% | 13.07 |
| DEMAG | 40.7% | 12.10 |
| NORMAL | 39.5% | 11.80 |

REDUC(감속기 고장)는 원래 토크 변동이 크므로 훨씬 많이 남는다. 가장 쉬운 클래스의 비중이 커지면 macro-F1이 유리해진다. **그래서 위 표를 클래스별 재현율로 보고했다.** 참고로 macro-F1은 0.974 → 0.9915지만 이 값은 혼합 왜곡을 포함한다.

다만 DEMAG(12.10)와 NORMAL(11.80)의 토크 변동은 거의 같다. **우리가 문제 삼는 DEMAG↔NORMAL 구분에 대해서는 게이트가 라벨 정보를 갖지 않는다.**

# Part III. 종합

## 15. 두 실험을 잇는 결론 — 같은 정보, 다른 역할

CAN 결합 실험에서 `rpm_dynamics`(RPM 표준편차·최소·최대·고유값 수)를 **특징으로** 추가했을 때 효과는 +0.035%p로 사실상 0이었다.

그런데 같은 `rpm_std`를 **게이팅 변수로** 쓰니 DEMAG 재현율이 +2.37%p 올랐다.

> **특징으로서의 가치와 메타정보로서의 가치는 다르다.** 모델에 변동 정보를 넣어도 스스로 "이 구간은 판단하지 않겠다"를 학습하지는 않는다. 그 판단은 밖에서 내려야 한다.
> 

CAN 결합 실험은 음성 결과였지만, 그 실험이 만들어낸 OOF 예측과 CAN 요약값 덕분에 오류 분석이 가능했다. **음성 결과가 낭비가 아니었다.**

### 15-1. 참조데이터(Other)의 최종 쓰임

> **한 줄: 모델 입력으로는 탈락, 운용 규칙의 근거로는 핵심.** 25개 통계 중 실제로 쓰는 것은 1개다.
> 

#### 실제로 쓰이는 것

| # | 신호 | 용도 | 효과 |
| --- | --- | --- | --- |
| 1 | **`torque_act_std`** | **진단 시점 게이팅** (§13-1) | DEMAG 미검출 4.11% → **0.46%**, 커버리지 53.7% (홀드아웃 검증) |
| 2 | `rpm_mean` | 학습에 쓰던 RPM이 실제 CAN과 맞는지 **검증** | 최대 오차 **0.000** (3차종 전부) |
| 3 | `rpm_std` | 차선 게이트 (참고용) | 미검출 4.11% → 1.54% |

**1번이 CAN의 최대 성과다.** 그리고 이것은 CAN 없이는 원리상 불가능하다.

- 토크는 PNG 특징에도, 라벨링 JSON에도 없다.
- 모델 입력의 `rpm` 채널은 **조각 안에서 상수**다. 입력 로딩 단계에서 `max|chunk_rpm − rpm_expected| = 0.000`으로 확인했다.
- 즉 **모델은 구조적으로 조각 내 변동을 표현할 수 없다.** 창 안에서 운전이 얼마나 변했는지는 CAN만 안다. 그리고 그것이 오류의 80%를 가르는 변수였다.

#### 시험했으나 기각된 것

| 대상 | 결과 |
| --- | --- |
| CAN 25개 전체를 입력 특징으로 결합 | +0.058%p, 구간 [−0.049, +0.173]%p → **기각** (홀드아웃에서 −0.058%p로 재확인) |
| 모터 온도 평균 | +0.004%p → 기각 |
| 토크 평균·표준편차 (특징으로) | +0.033%p → 기각 |
| RPM 변동 통계 (특징으로) | +0.035%p → 기각 |
| 인버터 온도 | A3에서 0.881 → 0.873 하락 → 기각 |

기각 이유는 정보가 없어서가 아니다. CAN 단독 F1이 0.53으로 판별력은 분명히 있는데, 기존 모델이 RPM을 보조 입력과 차수축 정규화에 이미 쓰고 있어 **정보가 중복**됐다(§7-1).

| --- | --- |
| 오류 분석의 좌표계 | 146,880구간 전체에 CAN을 붙여 둔 덕분에 운전 조건별 성능 분해가 가능해짐 |
| 온도 실험의 정체 | A3에서 기각한 온도가 모터 온도가 아니라 **인버터 온도**였음을 확인 |
| 코드 버그 | 연결 키의 seq 누락 → 센서 파일 **36.3%(13,869개)**가 덮어쓰기 대상이었음 (§4-2) |
| 검증된 음성 결과 | "CAN 결합은 효과 없다"를 정량적으로 확정 |

#### 만들었지만 안 쓰는 것

- 25개 통계 중 **22개** (토크 min/max/고유값수, 온도 5종, 목표토크 5종 등)
- 배터리 데이터 (이번 작업 범위 밖)

25개를 다 만든 것은 **어느 것이 쓸모 있을지 미리 알 수 없었기 때문**이다. 결과적으로 가장 쓸모 있던 것이 예상 밖의 `torque_act_std`였다.

## 16. 한계와 다음 단계

### 16-1. 한계

1. **탐색적 비교다.** 4개 후보를 같은 교차검증에서 비교했으므로, 여기서 고른 구성을 최종 채택하려면 별도 주행 세션으로 재검증해야 한다.
2. **CAN 통계는 PNG 전체 구간의 값이다.** 실시간으로 앞부분만 관측한 조기 진단 성능을 뜻하지 않는다.
3. **신뢰구간은 조건부다.** 이미 계산된 OOF 예측을 고정한 재표집이므로, 모델을 매번 다시 학습할 때의 변동 전체는 포함하지 않는다.
4. **저장된 모델은 평가용이다.** 전체 데이터로 재학습한 배포 모델이 아니다.
5. **게이팅 결과도 같은 CV에서 발견했다.** 변수(rpm_std / rpm_span / torque_std 중 최선)와 임계값을 이 데이터를 보고 골랐고, 가설 자체도 이 데이터에서 나왔다.

### 16-2. 왜 홀드아웃이 필요한가

지금까지의 모든 숫자는 **같은 3폴드 교차검증 위에서** 나왔다. 그리고 그 위에서 결정을 여러 번 내렸다.

| 결정한 것 | 어디서 골랐나 |
| --- | --- |
| 51ch vs 48ch vs 81ch vs 87ch | 같은 CV |
| 커널 수 9,996 유지 | 같은 CV |
| 인버터 온도 기각 | 같은 CV |
| CAN 결합 4종 비교 | 같은 CV |
| 게이팅 변수와 임계값 | 같은 CV |

**같은 데이터를 여러 번 들여다보고 고른 것은 그 데이터에서만 잘 맞을 수 있다.** 교차검증은 훈련 성능보다 정직하지만, 선택을 그 위에서 반복하면 그 폴드들도 결국 학습에 쓰인 것이나 마찬가지가 된다. 사람이 중간에서 옵티마이저 역할을 한 셈이다.

홀드아웃은 이 문제를 끊는다. 세션을 **미리** 나누고, 최종 테스트 세션은 모든 결정이 끝날 때까지 **한 번도 보지 않는다.** 마지막에 딱 한 번 평가한다. 그러면 0.974도, 미검출 1.04%도 탐색 결과가 아니라 **독립 추정치**가 된다.

발표 관점에서도 "교차검증에서 0.973"과 "한 번도 쓰지 않은 주행 세션에서 0.97x"는 무게가 다르다. 현재 구조에서는 **추가 학습 한 번**이면 된다.

### 16-2-1. 홀드아웃 결과 (2026-09-15 실행 완료)

사전 등록 [HOLDOUT_PLAN.md](https://app.notion.com/p/HOLDOUT_PLAN.md) / 결과 [holdout/HOLDOUT_RESULT.md](https://app.notion.com/p/holdout/HOLDOUT_RESULT.md). **세 가설 모두 통과했다.**

## 17. 발표에서 쓸 문장

> CAN 참조데이터에서 추출한 25개 통계 특징을 기존 87채널 모델에 결합해 3개 차종 × 3폴드 교차검증으로 평가했다. 평균 macro-F1 변화는 +0.058%p이며, 주행 세션 단위 부트스트랩 95% 신뢰구간이 0을 포함해 유의한 개선은 확인되지 않았다. CAN 단독으로는 F1 0.53의 판별력을 보이므로 정보가 없는 것은 아니며, 기존 모델이 RPM을 보조 입력과 차수축 정규화에 이미 활용하고 있어 정보가 중복된 것으로 해석된다.
> 
> 
> 이 과정에서 확보한 48,744건의 예측 기록을 분석한 결과, 남은 오류의 79.6%가 DEMAG↔NORMAL 혼동이며 **정속·저부하 구간에 집중**됨을 확인했다. 조각 내 토크 변동이 큰 구간에서만 진단하면 DEMAG 미검출이 4.51%에서 1.04%로 줄어든다. 이는 모델 개선이 아니라 진단 시점을 선택하는 운용 전략이다.
> 

홀드아웃까지 포함한 버전은 다음과 같다.

> CAN 참조데이터 183,600개 파일에서 25개 통계 특징을 추출해 87채널 모델에 결합했으나, 3차종 교차검증과 홀드아웃 모두에서 유의한 개선이 없음을 확인했다. 대신 이 데이터를 **진단 시점을 선택하는 기준**으로 활용하는 방법을 찾았다. 실제 토크의 표준편차가 큰 동적 구간에서만 판정하면 DEMAG 미검출률이 4.11%에서 0.46%로 감소하며, 이 임계값은 개발 데이터에서만 결정해 테스트 데이터에 적용한 것이다. 토크 변동 정보는 스펙트로그램 특징에 존재하지 않으므로 CAN 데이터가 없으면 불가능한 접근이다.
> 
> 
> 또한 최종 87채널 구성을 학습에 사용하지 않은 주행 세션에서 검증해 macro-F1 0.976을 기록했다. 세 가지 판정 기준은 모두 실험 전에 문서로 고정했다.
> 

"안 해봤다"에서 **"해봤고, 효과가 없음을 정량적으로 검증했으며, 그 과정에서 더 중요한 것을 찾았고, 그것을 독립 데이터로 확인했다"**로 바뀐다.

## 18. 재현 방법

### CAN 결합 실험

```powershell
python can_fusion_experiment.py --self-test                          # 연결·누수 차단 자체검사
python can_fusion_experiment.py --audit-only --out can_fusion_audit  # 연결 감사만
.\run_can_fusion.ps1                     # 자체검사 → 실험(재개) → 집계
.\run_can_fusion.ps1 -Detached           # 콘솔과 분리해 실행
.\run_can_fusion.ps1 -StatusOnly         # 진행 상황
.\run_can_fusion.ps1 -SkipExperiment     # 완료된 폴드로 보고서만 재생성
.\watch_can_fusion.ps1 -WaitSeconds 540 -AutoRestart   # 대기 → 보고 → 죽으면 재시작
```

`can_fusion_experiment.py`를 수정하면 소스 SHA-256이 달라져 재개가 거부된다(의도된 동작). 러너는 같은 출력 폴더에 두 프로세스가 동시에 쓰는 것을 막는다.

### 오류 분석

```powershell
python 오류분석_운전조건.py              # Part II 의 모든 표를 재생성
python 오류분석_운전조건.py --model all25  # CAN 결합 모델로 같은 분석
```

저장된 예측과 CAN 요약값만 읽는다. 재학습·특징 재추출이 없어 수 초 안에 끝난다. 검증 장치: 폴드 간 샘플 중복 없음, CAN 조인에서 행 손실 없음(`validate="one_to_one"`), 게이트 임계값은 차종별로 계산.

### 홀드아웃 검증

```powershell
python holdout_experiment.py --smoke     # 소규모 작동 검사 (약 3분)
python holdout_experiment.py             # 본 실험 (약 36분)
python holdout_experiment.py --resume    # 중단 시 재개
python summarize_holdout.py              # 사전 기준으로 판정, HOLDOUT_RESULT.md 생성
python summarize_holdout.py --partial    # 진행 중 부분 결과만 확인
```

입력 캐시(`x.npy`, 차종당 약 11GB)는 차종이 끝날 때마다 자동 삭제된다(`--keep-cache`로 유지). 사전 등록 문서는 [HOLDOUT_PLAN.md](https://app.notion.com/p/HOLDOUT_PLAN.md), 결과는 [holdout/HOLDOUT_RESULT.md](https://app.notion.com/p/holdout/HOLDOUT_RESULT.md).

입력 캐시 `x.npy`(차종당 약 10.5GB, 총 31.6GB)는 원본 특징데이터에서 재생성 가능하므로 결과 확정 후 삭제했다. 폴드별 `rocket_features.npy`(총 5.4GB)는 남아 있으며, 지우면 헤드만 다시 학습할 때 MiniRocket 변환(폴드당 약 9분)을 다시 해야 한다.
