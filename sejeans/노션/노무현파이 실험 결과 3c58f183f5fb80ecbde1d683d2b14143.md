## 2. 스레드·배치가 무의미하다

같은 커널에서 네 조건 전부 **±3% 안**이야.

- **스레드 1 vs 4**: 최대 0.6% 차이. 스크립트가 `mr.n_jobs`를 실제로 덮어쓰는데도(코드 확인함) 변화 없음 → **MiniRocket이 Pi에서 병렬화를 못 함**
- **배치 1 vs 32**: 청크당 455 → 448ms, 1.5%. i9에서 배치32가 2.5배 이득이었던 건 16코어에 청크를 펼쳤기 때문이고, 코어 4개로는 펼칠 자리가 없음

**실차 관점에서 중요해.** 차에서는 10초에 하나씩 들어와서 배치를 못 쌓는데, 배치가 어차피 무의미하니 **벤치 조건 = 실차 조건**이야. 그리고 코어 하나만 쓰니 나머지 3개는 다른 기능에 남아.

## 3. dilation 상한이 하드웨어 무관하게 재현됨

|  | 2,436 → 9,996 (커널 4배) |
| --- | --- |
| Pi 4 | 412 → 455ms (**+10%**) |
| PC 1스레드 | 99.1 → 108.6ms (**+10%**) |

배율까지 똑같아. MiniRocket의 dilation 개수 상한(32) 때문에 두 모델의 실제 연산 구조가 거의 같다는 게 **구조적 현상**으로 확정됐어.

그리고 **4,956은 2,436에 완전히 지배당해** — 성능 차이 0.002인데 35ms 느리고 모델은 두 배야. 커널을 줄여야 할 상황이 오면 후보는 2,436 하나뿐이고.

진짜 계단은 1,176 ↔ 2,436 사이에 있어. 여기서 지연이 227 → 412ms로 **1.8배 뛰는데**, 대신 DEMAG recall이 0.955 → 0.923으로 떨어져. 22배 여유가 이미 있으니 그 거래를 할 이유가 없어.

## 4. transform이 99.7%

9,996 커널 단건 기준 MiniRocket 452.1ms / 전처리 1.35ms / 분류기 1.57ms.

**분류기 최적화는 완전히 무의미해.** i9에서 97%였는데 Pi에서 더 극단적으로 나왔고, 이제 두 하드웨어에서 확인됐어.

## 6. 시동 대기시간 (새로 발견)

`jit_warmup_s`가 배치에 따라 크게 달라져. 배치1이면 1.4초인데 배치32면 **43초**야.

실차에서는 "시동 후 첫 진단까지의 대기시간"이 되는데, 배치1로 운용하니까 **1.4초**야. 문제없는 수준이고 발표에서 언급해두면 측정을 꼼꼼히 했다는 인상을 줘.

## 결론

**87채널 / 9,996커널 확정.** 커널 축소도 채널 축소도 할 이유가 없어졌어. Pi 4는 실차 도메인 컨트롤러보다 낮은 사양이라 이 22배 여유는 **하한선**으로 볼 수 있고.

발표 문장:

> 라즈베리파이 4에서 실제 배포 모델로 측정한 결과, 10초 분량 신호를 0.46초에 판정합니다. 실시간 요건 대비 22배 여유이며, 4코어 중 1코어만 사용하고 40분 연속 부하에서도 클럭 저하가 없었습니다.
> 

**한 가지 정직하게 남길 것.** 이 측정은 MiniRocket + 분류기 구간이고, 실차에서는 앞에 STFT·특징추출 단계가 붙어. 9.5초가 남아 있어서 문제될 가능성은 낮지만 "전처리는 별도 측정 예정"이라고 명시해두는 게 안전해.
