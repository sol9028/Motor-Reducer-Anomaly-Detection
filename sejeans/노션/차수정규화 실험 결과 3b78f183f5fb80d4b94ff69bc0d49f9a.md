## 1. 무엇을 왜 했는가

### 문제

A4(확장특징) 채택 후에도 세 차종의 남은 오류가 **DEMAG↔︎NORMAL 한 경계**에
집중돼 있었다. KONA DEMAG recall 이 0.883 으로 가장 낮았다.

### 원인 가설

**rpm 이 다르면 같은 고장이 다른 주파수에 나타난다.**

기존 특징은 전부 “절대 주파수 bin 위치” 기준이다. 그런데 모터 결함 주파수는
회전수에 비례해서 움직인다. 그러면 같은 DEMAG 고장인데도 rpm 2000 일 때와
rpm 5000 일 때가 전혀 다른 자리에 찍히고, 모델은 하나의 패턴으로 배울 수 없다.

### 해결책 (차수정규화, order normalization)

주파수축을 rpm 에 비례해 늘렸다 줄여서, **고장이 항상 같은 자리에 오게** 만든다.

```
        rpm 2000                    rpm 5693
절대축   결함이 268 bin 자리      결함이 763 bin 자리     ← 다른 자리
차수축   결함이 0.597 자리        결함이 0.597 자리       ← 같은 자리!
```

축의 의미가 “몇 번째 주파수 bin” 에서 **“회전수의 몇 배(=차수)”** 로 바뀐다.

## 2. 물리적 근거 — 라벨링 JSON 전수 측정

“결함 주파수가 rpm 에 비례한다” 는 건 가정이 아니라 **측정된 사실**이다.
전문가가 표시한 결함 대역(annotations.polygons)의 위치를 rpm 으로 나눠 봤다.

**K = 결함위치_bin / rpm**

| 클래스 | IONIQ | KONA | NIRO | 해석 |
| --- | --- | --- | --- | --- |
| DEMAG | 0.1333 | 0.1344 | 0.1342 | 차종 무관 일정 (std ≤0.002) |
| ECC10 | 0.1088 | 0.1087 | 0.1089 | 차종 무관 일정 |
| ECC20 | 0.1091 | 0.1089 | 0.1091 | ECC10 과 **동일** |
| REDUC | 0.1789 | 0.1411 | 0.1420 | IONIQ 만 다름 (감속비 차이) |

**K 가 차종을 넘어 일정하다** = 결함 주파수는 rpm 의 고정 배수다. 차수정규화의 근거.

부수적으로 알게 된 것: **ECC10 과 ECC20 의 K 가 같다.** 두 클래스는 주파수
위치가 아니라 **진폭(심각도)** 으로 갈린다는 뜻이다. 차수정규화는 위치를
정렬하는 변환이라 ECC10↔︎ECC20 구분에는 원리적으로 도움을 줄 수 없다.

## 3. 이전 시도(3단계)는 왜 실패했는가

차수정규화는 3단계에서 이미 한 번 시도했고 “부족” 판정이 났었다(분리도 1.540 → 1.587).
이번에 원인을 찾았다. **버그였다.**

3단계는 `REF_RPM = 3300` 을 썼다. 그런데 실제 rpm 범위는 1781~5693 이다.
기준보다 빠른 조각은 축이 원본 범위를 넘어가 **잘려나간다(NaN)**.

| REF_RPM | 유효비율 평균 | 최악 | 잘린 이미지 |
| --- | --- | --- | --- |
| 3300 (3단계) | 92.3% | 58.0% | 225장 중 **120장** |
| 4600 | 99.4% | 80.8% | 18장 |
| **5700** | **100.0%** | **100.0%** | **0장** |

즉 3단계는 표본 절반 이상이 축 윗부분을 잃은 상태에서 측정한 값이었다.
`REF_RPM ≥ max(rpm)` 으로 두면 항상 압축만 일어나 잘림이 원리적으로 0이 된다.

> 본데이터는 rpm 범위가 **177~9023** 으로 샘플보다 훨씬 넓어서
`REF_RPM = 9100` 으로 설정했다. 이 값을 넘으면 추출 스크립트가
시작 전에 자동 중단하고 올릴 값을 알려준다(몇 시간 돌린 뒤
잘림을 발견하는 사고 방지).

## 4. 왜 절대축을 ’대체’하지 않고 ’추가’했는가 ← 중요

예비 검증(표본 225장)에서 차수축 단독은 이런 결과가 나왔다.

|  | 절대축 | 차수축 단독 |
| --- | --- | --- |
| DEMAG recall | 80.0% | **84.4%** |
| 전체 정확도 | **68.0%** | 61.3% |
| ECC10 recall | **64.4%** | 53.3% |
| REDUC recall | **77.8%** | 60.0% |

**차수축은 DEMAG 를 사고 ECC10/REDUC 를 판다.** 노이즈가 아니라 구조적 현상이다.

이유: 차수정규화는 rpm 을 **일부러 지우는** 변환이다. 그런데 rpm 은
ECC/REDUC 에는 실제 판별정보다. 예를 들어 NIRO 는 DEMAG 가 4591~5693,
NORMAL 이 1951~3398 이라 rpm 만으로 갈린다. 교란을 지우면 진짜 신호도 같이 지워진다.

→ **둘은 상보적이므로 택일이 아니라 결합이 답이다.**
절대축 특징과 차수축 특징을 모두 채널로 넣고, 모델(LogisticRegression)이
클래스별로 가중치를 정하게 한다.

## 5. 구현

### 특징 컬럼 구성 (`모터_특징추출_v2.py`)

parquet 컬럼이 21 → **33개**가 됐다. `ord_` 접두사가 차수축이다.

| 그룹 | 컬럼 | 개수 |
| --- | --- | --- |
| 기본 4특징 | peak_freq_bin, band_start, band_end, rms | 4 |
| rpm | rpm | 1 |
| 확장특징 (절대축) | band_ratio_0~7, centroid, entropy, rolloff, log_flatness | 12 |
| **확장특징 (차수축)** | **ord_band_ratio_0~7, ord_centroid, ord_entropy, ord_rolloff, ord_log_flatness** | **12** |
| 메타/기타 | group_key, fault_class, time_idx, temperature | 4 |

학습에 쓰는 피처는 29개 (메타 4개 제외) → 29 × 3센서 = **87채널**

### 처리 흐름

```
PNG 조각 → LUT 역변환 → 에너지 맵 (1280 bin)
                          ├─ 그대로 특징 추출 ─────→ band_ratio_0~7, centroid, ...
                          └─ rpm 비례 리샘플링 ──→ ord_band_ratio_0~7, ord_centroid, ...
                             (to_order_axis)
```

### 설계 판단 2개 (팀원 참고)

**(1) 차수축은 조각(split) 단위로 변환한다.**
rpm 은 조각마다 다르다. 실측하니 멀티스플릿 그룹의 **90%가 rpm spread > 50**,
중앙값 677rpm, 최대 1879rpm 이었다. 병합된 배열에 그룹 대표 rpm 하나로
리샘플링하면 대부분 구간이 틀린 배율로 늘어난다. 그래서 병합 전 원본 조각을
다시 읽어 조각마다 따로 변환한다. → 이미지를 두 번 읽는 게 추출 시간 증가 원인.

**(2) `extract_ext_features` 를 NaN 안전 집계로 바꿨다.**
기존 `sum()`/`mean()` 은 NaN 을 전파해서 한 행만 NaN 이어도 열 전체가 죽는다.
절대축은 NaN 이 없어 **A4 수치는 그대로 재현된다**(실제로 확인됐다, §6 참조).

## 7. 판정

**채택 권고.** 근거 세 개가 모두 충족됐다.

1. **성능**: DEMAG recall 전 차종 상승. KONA +5.4%p 는 판정 기준(+3%p)의 1.8배.
macro-F1 도 전 차종 상승, 하락한 지표가 하나도 없다.
2. **안정성**: 폴드 편차가 오히려 줄었고(±0.011 → ±0.005), timestamp CV
(엄격 프로토콜) 에서 나온 수치다.
3. **비용**: 학습 38분으로 실용 범위. 경량화 목표와 충돌하지 않는다.

가장 취약했던 KONA 가 가장 크게 개선된 점이 특히 의미 있다.
“rpm 교란이 DEMAG↔︎NORMAL 혼동의 원인” 이라는 가설이 그대로 검증됐다.
