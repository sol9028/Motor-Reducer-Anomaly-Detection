# DEMAG↔︎NORMAL 문제 — 원인 규명과 개선 작업 공유

> 3차 발표 「트랙 1·2」를 실제로 실행한 결과입니다.
원인을 찾다가 **파이프라인 자체의 오류 2건**을 발견해서, 그것부터 고쳤습니다.
>

## 0. 한 장 요약

3차 발표에서 남은 과제는 **DEMAG(자석 열화) ↔︎ NORMAL 혼동**이었습니다.
원인을 파고들었더니, 모델 문제가 아니라 **PNG → CSV 변환 단계가 잘못돼 있었습니다.**

|  | 무엇이 문제였나 | 상태 |
| --- | --- | --- |
| **① 색 → 숫자 변환** | 밝기로 계산해서 **가장 약한 신호와 가장 센 신호가 같은 값**이 됨 | ✅ 수정 완료 |
| **② 임계값 방식** | `band_start` 컬럼의 **80~95%가 상수 0** = 정보량 0인 죽은 컬럼 | ✅ 수정 완료 |
| **③ rpm 미사용** | 라벨링 JSON에 회전속도가 있는데 안 쓰고 있었음 | ✅ 추가 완료 |
| ④ 확장 특징 | 4개 특징으로는 DEMAG의 “에너지 재분배”를 표현 못 함 | ⏸ **보류** |
| ⑤ 차수 정규화 | rpm에 맞춰 주파수축을 늘렸다 줄이기 | ⏸ **보류** |

**①②③은 성능과 무관하게 “틀린 것을 고친 것”**입니다. ④⑤는 근거가 부족해서 아직 판단하지 않았습니다.

## 왜 다른 클래스는 잘 됐는데 DEMAG만 안 됐나

먼저 이게 궁금하실 겁니다. 변환이 망가졌다면 ECC10/ECC20/REDUC도 같이 망가져야 하는데, 그것들은 잘 맞았죠.

**고장마다 “어디를 보고 구별하는지”가 다르기 때문입니다.**

| 고장 | 구별 단서 | 망가진 변환의 영향 |
| --- | --- | --- |
| ECC10 / ECC20 (축 틀어짐) | 신호가 **어느 주파수에** 나타나는가 | 위치는 안 망가짐 → 영향 적음 |
| REDUC (기어 결함) | 신호가 **어느 주파수에** 나타나는가 | 위치는 안 망가짐 → 영향 적음 |
| **DEMAG (자석 열화)** | 주파수는 그대로, **에너지 크기가 재분배**됨 | **크기 축이 망가짐 → 직격탄** |

실제 측정값입니다:

```
IONIQ Vib_TM의 peak_freq_bin (신호가 나타나는 위치)
  NORMAL  725      DEMAG  720   ← 거의 같음. 위치로는 구별 불가
  ECC20   565                   ← 확 다름. 위치만으로 구별 가능
```

DEMAG는 **위치가 아니라 크기로만 구별되는 유일한 고장**입니다.
그런데 우리 변환이 정확히 그 크기 축을 망가뜨리고 있었습니다.

## ① 색 → 숫자 변환 고치기 (LUT 역변환)

### 근거

스펙트로그램 PNG는 신호 세기를 **색**으로 칠한 그림입니다. 파란색이 약하고 빨간색이 셉니다.
이걸 다시 숫자로 되돌려야 하는데, 기존 코드는 **RGB 밝기의 평균**을 썼습니다.

```python
energy = np.sqrt(np.mean(arr ** 2, axis=2))   # 기존 — 밝기 평균
```

문제는 이 그림이 쓰는 색상표(**jet 컬러맵**)가 **밝기 순서대로 되어 있지 않다**는 겁니다.

```
신호 세기:  약함 ──────────────────────────► 강함
색:        짙은 남색 → 하늘 → 초록 → 노랑 → 주황 → 짙은 빨강
밝기:        0.45     0.7   0.8   0.95   0.7     0.45
                ▲                                  ▲
                └──────── 밝기가 똑같다! ───────────┘
```

**가장 약한 신호(짙은 남색)와 가장 센 신호(짙은 빨강)가 둘 다 밝기 0.45**로 계산됩니다.
밝기는 중간(노랑)에서 최고였다가 다시 떨어지기 때문입니다. 실측해보니 **부호가 6번 뒤집힙니다.**

### 방법

색상표를 **거꾸로 되짚는 표**를 미리 만들어 둡니다. 이걸 **LUT 역변환**이라고 부릅니다.

> 📖 **LUT(Look-Up Table, 조회표)란?**
계산하는 대신 미리 답을 적어둔 표입니다.
여기서는 “이 색(R,G,B) → 원래 신호 세기는 얼마” 를 미리 채워둔 표입니다.
픽셀마다 계산하지 않고 표에서 꺼내 쓰기 때문에 매우 빠릅니다.
> 

```
[기존] 색 → 밝기 평균 → 숫자          (틀림. 순서가 뒤죽박죽)
[개선] 색 → LUT 조회 → 원래 숫자      (맞음. 색상표를 그대로 되짚음)
```

표 크기는 RGB 각 축을 64칸으로 쪼갠 **64×64×64 격자**이고, 용량은 0.26MB로 작습니다.

### 검증

먼저 **이 그림이 정말 jet 컬러맵이 맞는지**부터 확인했습니다. 12개 후보 색상표와 대조한 결과:

- 9장 중 7장이 jet에서 최적 (나머지 2장도 jet끼리 섞인 색으로 설명됨, 오차 56.39 → 3.16)
- 오차가 **색 경계에서만 커짐**(평탄 9.01 vs 경계 15.98) → 이미지 압축 노이즈이지 색상표 불일치가 아님

### 결과

```
rms 값 범위    0.14 ~ 0.87   (뭉개짐 없음)
rms == 0       0.00%
```

### 기대효과

DEMAG의 유일한 단서인 **에너지 크기 축이 물리적으로 올바르게** 됩니다.
성능이 오르든 말든 **이건 틀린 걸 고친 것**이라, 반드시 적용해야 합니다.

## ② 죽어 있던 컬럼 살리기 (행별 기저 제거)

### 근거

기존 코드는 이미지 **전체**에서 상위 10%만 남기는 방식이었습니다.

```python
threshold = np.percentile(energy, 90)   # 전체 기준 하나의 선
mask = energy >= threshold
```

그런데 스펙트로그램은 **저주파가 원래 밝고 고주파가 원래 어둡습니다.** 고장과 무관하게 그렇습니다.
전체에 선 하나를 그으면:

```
   높은 주파수 │ ▁▁▁▁▁▁▁▁  ← 원래 어두움. 통째로 탈락
              │
   ─────────── │ ── 임계선 하나 ──
              │
   낮은 주파수 │ ████████  ← 원래 밝음. 통째로 통과
```

`band_start`(신호가 시작되는 가장 낮은 주파수)가 **항상 화면 맨 아래(0)에 붙어버립니다.**

실측한 기존 CSV:

| 센서 | `band_start`가 0인 비율 |
| --- | --- |
| Vib_Motor | **94.6%** |
| Vib_TM | **80.7%** |

**컬럼의 대부분이 상수 0**입니다. 12개 채널 중 3개(센서당 1개)가 사실상 죽어 있었습니다.

### 방법

임계선을 하나만 긋지 말고, **주파수 줄마다 따로** 긋습니다.
“절대적으로 밝은가”가 아니라 **“그 주파수 치고 유별나게 밝은가”**로 바꾸는 겁니다.

```python
def row_detrend(energy):
    med = np.median(energy, axis=1, keepdims=True)          # 줄별 중앙값
    mad = np.median(np.abs(energy - med), axis=1, ...)      # 줄별 산포
    return (energy - med) / (1.4826 * mad)
```

> 📖 **용어 풀이**
- **중앙값(median)**: 값을 크기순 정렬했을 때 한가운데. 평균과 달리 극단값에 안 흔들립니다.
- **MAD**: 중앙값에서 얼마나 떨어져 있는지의 중앙값. 표준편차의 튼튼한 버전입니다.
- **1.4826**: MAD를 표준편차와 같은 눈금으로 맞추는 상수입니다.
- **왜 평균이 아니라 중앙값?** 스펙트로그램은 몇몇 픽셀이 유독 밝은 분포(꼬리가 두꺼움)라, 평균을 쓰면 그 몇 개에 끌려갑니다.
> 

비유하자면 시험 점수를 **원점수가 아니라 과목별 등수**로 바꾸는 것과 같습니다.
수학 평균이 30점이고 영어 평균이 80점이면, 원점수 60점의 의미가 과목마다 다르니까요.

⚠️ **주의**: 이 변환값은 “특이한 정도”이지 **실제 크기가 아닙니다.**
그래서 `rms`와 확장 특징은 변환 **전의 원래 에너지**에서 뽑습니다. 임계 판정에만 씁니다.

### 결과

```
                기존      개선
Vib_Motor      94.6%  →   0.0%
Vib_TM         80.7%  →   0.1%
Current_U        —        1.8%
고유값 개수       ~1    →   403~1279개
```

### 기대효과

**죽어 있던 채널 3개가 실제 신호를 담게 됩니다.** 12채널 중 3개를 공짜로 되찾는 셈입니다.

## ③ 회전속도(rpm) 넣기

### 근거

같은 고장이라도 **모터가 빨리 돌면 신호도 높은 주파수로 올라갑니다.** 당연한 물리입니다.
rpm을 모르면 모델은 “고장이라 주파수가 높은 건지, 빨리 돌아서 높은 건지” 구별할 수 없습니다.

3차 발표 트랙 2에서 “메타데이터 활용”으로 계획했던 부분인데, **`Other` 폴더는 용량이 너무 커서** 대안을 찾았습니다.

→ **라벨링 JSON(1.5MB)에 이미 들어 있었습니다.**

```json
"metadata": { "car_model": "IONIQ", "temperature": 42.29, "speed": 2902.8892 }
                                                            ↑ 이게 rpm
```

측정해보니 rpm의 영향력이 매우 큽니다:

- 주파수 위치와 rpm의 상관계수 **0.984 / 1.000 / 0.999** (차종별)
- **NIRO는 rpm 하나만으로 100% 분류**됨

### 방법 — 여기서 함정을 하나 발견했습니다

처음엔 “파일 하나에 rpm 하나”인 줄 알았는데, 실제로 열어보니:

```
같은 세션(같은 주행) 안에서
  22_08_12_11_12_18_zsplit002
     조각1: 2343 rpm
     조각2: 3272 rpm     ← 계속 변한다
     조각3: 4222 rpm
```

**가속 주행 데이터**였습니다. 그런데 우리 파이프라인은 이 조각들을 **가로로 이어붙여** 한 장으로 만듭니다.
즉 이어붙인 그림의 가로축은 시간이고, **구간마다 rpm이 다릅니다.**

세션당 rpm 하나만 붙이면 대부분 구간에 틀린 값이 들어갑니다. 그래서 **조각별 폭을 기억해뒀다가 구간마다 해당 rpm을 채웁니다.**

```python
for p, w in zip(image_paths, widths):
    rec = rpm_idx.get(p.stem)        # 조각 단위 조회
    rpm_col[x : x+w] = rec["rpm"]    # 그 구간만 채움
    x += w
```

### 결과

```
채움율                      100.0%
rpm 범위                    1,735 ~ 7,774
group 안에서 rpm 종류        평균 22.6개
rpm이 2종류 이상인 group      86.5%
```

### 기대효과

rpm이 상수가 아니라 **시간에 따라 변하는 채널**이 됩니다.
MiniRocket은 시계열 패턴을 읽는 모델이라, **가속 패턴 자체가 하나의 특징**이 됩니다. 온도도 같이 넣었습니다.

## ④ 확장 특징 (넣어뒀지만 판정은 보류)

### 근거

기존 4개 특징을 다시 보면:

```
peak_freq_bin  ← 위치
band_start     ← 위치
band_end       ← 위치
rms            ← 크기 (딱 하나, 그것도 전체 평균)
```

**위치 3개 + 크기 1개**입니다. DEMAG는 “저주파 30%→20%, 고주파 15%→25%” 같은 **재분배**인데,
전체 평균 하나로는 이걸 담을 그릇이 없습니다. 총량은 그대로일 수 있으니까요.

3차 발표 트랙 1의 “고조파 대역 에너지 비율, 스펙트럼 엔트로피 추가”가 바로 이 얘기입니다.

### 방법 — 12개 추가

| 특징 | 쉬운 설명 |
| --- | --- |
| `band_ratio_0` ~ `_7` | 주파수를 8등분해서 **각 칸이 전체의 몇 %인지**. 합이 항상 1 |
| `centroid` | 에너지의 **무게중심**. 저주파 쪽인지 고주파 쪽인지 |
| `entropy` | 에너지가 **넓게 퍼졌는지 한곳에 뭉쳤는지** |
| `rolloff` | 아래부터 더해서 **85%가 차는 지점**. 고주파 꼬리 길이 |
| `log_flatness` | **한 음처럼 뾰족한지, 잡음처럼 밋밋한지** |

핵심은 **비율**이라는 점입니다. 합이 1로 고정되니 **재분배가 그대로 숫자로 남습니다.**

### 현재 조치

컬럼은 **일단 다 뽑아두되, 채택 여부는 본데이터에서 판정**합니다.
CSV를 다시 뽑는 게 15시간짜리라, 나중에 학습에서 컬럼을 골라 쓰는 게 낫습니다.

## ⑤ 차수 정규화 (보류)

### 근거와 방법

rpm이 다르면 같은 고장도 다른 주파수에 나타납니다. 그러니 **rpm에 비례해 주파수축을 늘렸다 줄이면**
고장이 항상 같은 자리에 오게 만들 수 있습니다.

> 📖 **차수(order)란?**
주파수를 Hz가 아니라 **“회전수의 몇 배”**로 세는 방식입니다.
2배속으로 돌면 신호도 2배 주파수로 가지만, “회전수의 3배” 라는 값은 그대로입니다.
> 

### 현재 조치

**넣지 않았습니다.** 다만 rpm이 컬럼으로 들어가 있으니, 나중에 CSV 단계에서 후처리로 얹을 수 있습니다.
**PNG를 15시간 다시 읽을 필요는 없습니다.**

## 작업하면서 추가로 해결한 것들

원본 데이터에 돌리다가 터진 문제들입니다. 팀원분들이 같은 걸 겪을 수 있어 적어둡니다.

### 메모리 부족 (MemoryError)

조각이 90개가 넘는 그룹(`zsplit000`)은 이어붙이면 **가로 19만 픽셀**이 됩니다.
색을 조회하려고 자료형을 올리는 순간 **2.9GB를 한 번에** 잡아서 터졌습니다. 워커 8개가 동시에 그러니 더 심했고요.

**해결**: 큰 그림을 통째로 만들지 않고, **조각을 하나씩 숫자로 바꿔서 이어붙입니다.**
최대 메모리가 **2.9GB → 9.8MB**가 됐습니다. 결과는 이전 방식과 **완전히 동일**함을 확인했습니다(오차 0).

### 용량 초과

처음 추출해보니 **전체 106GB 예상**인데 디스크(C드라이브)에 155GB밖에 없었습니다.

**해결 2가지:**

1. **Parquet 형식으로 변경** (CSV 대신)
> 📖 **Parquet이란?** 숫자를 글자가 아니라 이진수로 저장하고 압축하는 형식입니다.
> 엑셀로는 못 열지만, pandas에서는 `read_csv` → `read_parquet` 한 줄만 바꾸면 됩니다.
> **읽는 속도도 더 빠릅니다** (글자를 숫자로 해석하는 과정이 없음).
2. **float16 저장** — 원본이 8비트 이미지(256단계)라 정밀도를 낮춰도 **정보 손실이 없습니다.**
실측 오차 0.00048로, 원본 자체의 오차 0.0039보다 **8배 정밀**합니다.

```
결과: 106GB → 약 43GB  (여유 112GB)
```

### 조용히 깨질 뻔한 컬럼 하나

전 컬럼 검사 중에 `flatness`가 **10⁻⁹ ~ 10⁰으로 9자릿수를 걸치는 것**을 발견했습니다.
float16으로 저장하면 **30%가 0으로 뭉개집니다.**

**해결**: 나눗셈 대신 **로그를 취해** `log_flatness`로 저장 (범위 −22 ~ 0). 뭉개짐 0.00% 확인.

> 못 잡았으면 컬럼 하나가 **망가진 줄도 모르고** 15시간을 돌릴 뻔했습니다.
