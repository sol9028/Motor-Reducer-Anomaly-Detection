## [슬라이드 5] 발견 ① — 색→숫자 변환이 틀려 있었다

**타이틀**: DEMAG를 파고들다 발견한 것 — 변환 단계의 물리적 오류

**문제 (왼쪽):**
- 스펙트로그램 PNG는 **jet 컬러맵**으로 그려진 이미지
- 기존 코드는 **밝기(brightness)** 로 에너지를 계산
- jet에서 밝기 최댓값은 **scalar 0.639(주황)** → 신호가 더 세면 짙은 빨강이 되며 **밝기가 오히려 떨어짐**

**측정 결과 (오른쪽, 표):**

| 차종/클래스/센서 | 피크 위치 불일치율 | 평균 오차 |
|---|---|---|
| IONIQ / NORMAL / Vib_TM | 100.0% | 536 bin |
| IONIQ / DEMAG / Vib_TM | 100.0% | 588 bin |
| KONA / DEMAG / Vib_TM | 100.0% | 997 bin |

→ 전체 높이 1280 bin 중 평균 500~1000 오차 = **사실상 무작위**

**핵심 질문 박스 — "그럼 3차 발표 성능(0.83~0.87)은 왜 나왔나?"**
> **틀렸지만 일관되게 틀렸기 때문.**
> NORMAL은 항상 561 근처, ECC20은 항상 780 근처로 모임 (클래스 내 산포 27~40).
> 값이 물리적으로 무의미해도, 클래스마다 다른 곳에 모이면 분류는 된다.

**비유 (아이콘 + 한 줄)**: 🔧 *눈금이 엉망인 자[尺] — 정확히 잴 순 없지만 "A가 B보다 길다"는 비교는 된다.*
→ 원래 차이가 큰 것(ECC·REDUC)은 구별되고, **차이가 거의 없는 DEMAG↔NORMAL은 구별 안 된다**

> 🖼️ **[이미지 자리 — 비워둘 것]** jet 컬러맵 밝기 곡선 그래프 (scalar 0.639에서 꺾이는 지점 강조) + 밝기 peak vs LUT peak 위치 비교 도식

## [슬라이드 8] 실험 해석 ① — rpm과 온도

**타이틀**: 넣을 것과 뺄 것을 어떻게 판단했나

**왼쪽: rpm — 채택 (조건부)**
- 효과는 **차종별로 엇갈림**: NIRO만 뚜렷한 이득(+0.029), KONA는 DEMAG recall −4.3%p
- **핵심 검사 — "지름길 학습(shortcut learning)" 여부**
  - rpm 값 하나만으로 학습했을 때 F1: **0.208 ~ 0.238** (판정 기준 0.4 미만 = 통과)
  - 클래스별 rpm 범위도 서로 **겹침** → rpm이 정답표가 되지 않음
- 📖 **왜 이 검사가 필요한가**: 샘플 데이터에서는 NIRO가 rpm만으로 100% 분류됐음.
  자석이 열화돼서 rpm이 높았던 게 아니라, **그날 빠르게 달렸을 뿐**(클래스당 주행 1회)
  → 실차에 올리면 고속도로 주행 중 멀쩡한 차에 DEMAG 오경보

**오른쪽: 온도 — 기각**
- 3차종 × 2지표 **전부 하락** (macro-F1 평균 −0.008, DEMAG recall −0.4~−2.0%p)
- 지름길은 아님 (temp단독 F1 0.213~0.279)
- **원인**: 온도는 청크(2000행) 안에서 사실상 **상수** → MiniRocket이 읽을 시계열 패턴이 없음.
  커널이 빈 채널에 분산되며 유효 특징의 밀도만 희석
- rpm은 **가속 곡선**이라는 패턴이 있었고 온도는 없었던 것이 둘의 운명을 가름
- → **채널 3개 절감으로 경량화 목표에도 부합**

> ⚠️ **단, 이 "온도"의 정체가 나중에 밝혀집니다** — 슬라이드 18에서 이어서 설명

## [슬라이드 10] 차수정규화 — 왜 필요했는가

**타이틀**: 남은 DEMAG 오류의 원인 — rpm이 같은 고장을 다른 자리에 찍는다

**문제 (왼쪽):**
- A4 채택 후에도 잔여 오류가 **DEMAG↔NORMAL 한 경계**에 집중. KONA recall 0.883으로 최저
- **원인 가설**: 모터 결함 주파수는 **회전수에 비례**해 움직이는데, 기존 특징은 전부 **절대 주파수 bin 위치** 기준
  → 같은 DEMAG인데 rpm 2000일 때와 5000일 때가 전혀 다른 자리에 찍힘 → 하나의 패턴으로 배울 수 없음

**해결책 (오른쪽, 도식):**
```
              rpm 2000            rpm 5693
절대축   결함이 268 bin 자리   결함이 763 bin 자리   ← 다른 자리
차수축   결함이 0.597 자리     결함이 0.597 자리     ← 같은 자리!
```
축의 의미가 "몇 번째 주파수 bin" → **"회전수의 몇 배(=차수)"** 로 바뀜

**물리적 근거 — 라벨링 JSON 전수 측정 (강조 박스):**
전문가가 표시한 결함 대역 위치를 rpm으로 나눔. **K = 결함위치_bin / rpm**

| 클래스 | IONIQ | KONA | NIRO | 해석 |
|---|---|---|---|---|
| DEMAG | 0.1333 | 0.1344 | 0.1342 | 차종 무관 일정 (std ≤0.002) |
| ECC10 | 0.1088 | 0.1087 | 0.1089 | 차종 무관 일정 |
| ECC20 | 0.1091 | 0.1089 | 0.1091 | **ECC10과 동일** |
| REDUC | 0.1789 | 0.1411 | 0.1420 | IONIQ만 다름 (감속비 차이) |

> **K가 차종을 넘어 일정하다 = 결함 주파수는 rpm의 고정 배수다.** 가정이 아니라 측정된 사실

**부수적으로 알게 된 것 (작게)**: ECC10과 ECC20의 K가 같음 → 두 클래스는 **위치가 아니라 진폭(심각도)** 으로 갈림.
차수정규화는 위치를 정렬하는 변환이라 ECC10↔ECC20 구분에는 **원리적으로 도움을 줄 수 없음**

> 🖼️ **[이미지 자리 — 비워둘 것]** 절대축 vs 차수축 스펙트로그램 정렬 비교 도식 (rpm이 다른 두 조각의 결함 위치가 차수축에서 겹치는 그림)

## [슬라이드 11] 차수정규화 — 두 번의 시도, 그리고 결합

**타이틀**: 첫 시도는 왜 실패했고, 왜 대체가 아니라 추가인가

**상단: 이전 시도(3단계)의 실패 원인 = 버그**
- 3단계는 `REF_RPM = 3300`을 사용. 그런데 실제 rpm 범위는 **1781~5693**

→ 표본 절반 이상이 축 윗부분을 잃은 상태에서 측정한 값이었음.
**`REF_RPM ≥ max(rpm)`으로 두면 항상 압축만 일어나 잘림이 원리적으로 0**
→ 본데이터 rpm 범위 177~9023 → `REF_RPM = 9100` 설정 (초과 시 스크립트 자동 중단)

**핵심 발견 — 계단(hold) 구조 (강조 박스, 오른쪽):**
- 파일 하나가 **250,000행 × 5열**인데, 컬럼별 **고유값이 20개뿐**
- 값 하나가 약 12,500행씩 그대로 유지됨
- 같은 참조데이터의 **배터리 CSV는 파일당 정확히 20행** → 스텝 수가 일치
- → **20스텝 CAN 신호를 진동 센서 샘플레이트(12.5kHz)에 맞춰 홀드시킨 것**

```
250,000행  →  (값, 구간길이) 20행  →  무손실 압축
```

**결과 (강조):**

| | 값 |
|---|---|
| 원본 | 5.28 TB |
| 처리 후 | **110 MB** (약 5만분의 1) |
| 소요 시간 | **48분** |
| 오류 | **0건** |

**무손실 검증**: 무작위 6개 파일을 20스텝 → 250,000행으로 복원해 원본과 대조 → **6/6 비트단위 완전 일치**

> 🖼️ **[이미지 자리 — 비워둘 것]** 계단 구조 도식 (250,000행 신호가 20개 계단으로 유지되는 그래프 + 압축 전후 용량 대비)

> 💬 **말할 것**: 압축을 풀면 5.28TB라 해제 자체가 불가능 → **zip에서 직접 읽는 방식**으로 처리

## [슬라이드 18] ⚠️ 역추적 — A3에서 기각한 "온도"의 정체

**타이틀**: 기존 파이프라인과 대조하다 발견한 것

**작업 (왼쪽):**
기존 `rpm_index.json`(440,640항목)의 값이 참조데이터의 무엇에서 나왔는지 **전수 대조**

| rpm_index 필드 | 실제 정체 | 일치율 | 최대 오차 |
|---|---|---|---|
| `rpm` | `rpm_mean` (3열 평균) | **100.000%** | 4.8e-05 |
| `temp` | **`temp_inv_mean` (4열 = 인버터 온도)** | **100.000%** | **0.0** |

**발견 (강조 박스, 크게):**
> ### A3 실험에서 기각한 "temperature"는 **인버터 온도**였습니다.
> ### `temp_motor`(모터 온도)는 **한 번도 사용된 적이 없습니다.**

**미사용 신호 정리 (오른쪽 표):**

| 채널 | 기존 사용 | 비고 |
|---|---|---|
| `rpm` | ✅ (`rpm_mean`) | A1에서 채택 |
| `temp_inv` | ⚠️ A3에서 기각 | **인버터** 온도 |
| `temp_motor` | ❌ **미사용** | 감속기 고장과 물리적 연관 가능 |
| `torque_ref` / `torque_act` | ❌ **미사용** | 완전히 새로운 신호 |
| min/max/std/nuniq 통계 | ❌ **미사용** | 기존엔 mean 1개만 사용 |

**부수 확인**: `rpm_index.json`은 전체의 **80.0%(146,880/183,600)만** 커버.
단, 15개 차종×조건 조합 전부에서 79.5~80.4%로 균일 → **클래스 편향은 없음**.
남은 20%(36,720개 파일)도 이제 사용 가능

> 💬 **말할 것**: "3차→4차에서 배운 교훈이 여기서 한 번 더 반복됐습니다.
> 무엇을 쓰고 있는지 정확히 확인하지 않으면, 기각 판정조차 틀린 대상에 내려집니다."

> 🖼️ **[이미지 자리 — 비워둘 것]** rpm_index.json ← 참조데이터 5채널 매핑 도식 (rpm/temp_inv만 연결선, 나머지 3채널은 끊긴 선으로 표시)

## [슬라이드 19] 새 채널의 판별력 — 그리고 지름길 경고

**타이틀**: 쓸 수 있는가, 써도 되는가

**상단: η² (클래스가 설명하는 분산 비율, 차종 내) 상위 항목**

| 특징 | IONIQ | KONA | NIRO | 평균 |
|---|---|---|---|---|
| `rpm_mean` | 0.250 | 0.216 | 0.254 | 0.240 |
| **`torque_act_std`** | 0.070 | 0.228 | 0.228 | **0.175** |
| `temp_inv_mean` | 0.112 | 0.183 | 0.147 | 0.147 |
| `torque_ref_max` | 0.053 | 0.177 | 0.167 | 0.132 |
| `temp_motor_nuniq` | 0.101 | 0.163 | 0.117 | 0.127 |

**중단: 참조데이터 요약만으로 5클래스 분류** (RandomForest, StratifiedGroupKFold 3, group=timestamp, macro-F1)

| 특징 구성 | IONIQ | KONA | NIRO | 판정 |
|---|---|---|---|---|
| `rpm+temp_inv` (기존 사용분) | 0.346 | 0.297 | 0.328 | 🟢 기준 내 |
| + `temp_motor` | 0.414 | 0.345 | 0.390 | 🟡 경계선 |
| + `torque` 2채널 | 0.438 | 0.364 | 0.411 | 🟡 경계선 |
| **전체 25특징 (5채널×5통계)** | **0.527** | **0.507** | **0.549** | 🔴 **기준 초과** |

기여도 순: **통계량 확장(min/max/std/nuniq) > temp_motor > torque**

**하단: ⚠️ 지름길(shortcut) 경고 — 강조 박스**
> 기존 판정 기준은 **"단독 F1 < 0.4 이면 지름길 아님"** 이었고, A1에서 rpm단독 F1은 0.208~0.238이었습니다.
> 그런데 **전체 25특징은 0.507~0.549로 기준을 명백히 초과합니다.**
>
> → 25특징을 통째로 넣으면 모델이 진동·전류 신호 대신 **주행 조건 메타정보로 클래스를 맞히는** 위험이 있습니다.
> → 채널 추가 시 **A3에서 했던 것처럼 단독 F1 검사를 반드시 선행**해야 합니다.

**연결 (한 줄, 크게):**
> **"쓸 수 있는 신호를 찾았다"와 "써도 된다"는 다른 문제입니다.**
> 슬라이드 8에서 세운 지름길 검사 원칙이 여기서 그대로 적용됩니다.

> ⚠️ **명시할 것**: 이번 작업은 **전처리까지**입니다. 학습 파이프라인(`모터_학습_v3.py`)에는 **아직 반영하지 않았습니다.**

> 🖼️ **[이미지 자리 — 비워둘 것]** 특징 구성별 단독 F1 막대그래프 (0.4 기준선을 붉은 점선으로 긋고, 25특징 막대만 초과 표시)

## [슬라이드 20] 남은 과제와 계획

**타이틀**: 여기서부터 무엇을 할 것인가

**트랙 1. 파이프라인 완결**
- **전처리(STFT·특징추출) 구간 지연 별도 측정** — 현재 실측은 MiniRocket+분류기 구간만
- 추출 검증 스크립트에 `ord_*` 항목 추가 (ord_band_ratio 합=1.0, NaN 비율, float16 언더플로우 확인)
- 81ch(band_ratio_7 계열 제외) 실행 후 87ch와 최종 비교

**트랙 2. 잔여 오류**
- DEMAG↔NORMAL은 433건으로 줄었으나 **여전히 남은 오류의 대부분**
- ECC10↔ECC20은 K값이 동일 → 위치가 아닌 **진폭(심각도)** 기반 특징이 필요 (차수정규화로는 원리적으로 해결 불가)

**트랙 3. 참조데이터 신호 반영 (신규)**
- **A5 후보 — `temp_motor` 단독 실험**: A3에서 기각한 건 인버터 온도였으므로 모터 온도는 미검증.
  η² 기준 `temp_inv`와 비슷한 수준이라 큰 기대는 어려우나, **한 번에 하나만 변경** 원칙상 별도 검증 가치 있음
- **A6 후보 — `torque` 실험**: `torque_act_std`가 η² 0.175로 rpm 다음 순위.
  ⚠️ 단, 0728 표본에서 `torque_ref`와 `torque_act`가 357개 중 **355개 파일에서 완전히 동일** →

  (3차 발표 트랙 2에서 세웠던 계획이므로 발표에서 명시적으로 정정)
- **rpm 통계 확장**: 현재 `rpm_mean` 1개만 사용. `rpm_std/min/max` 추가는 비용이 거의 0
- **커버리지 20% 회복**: `rpm_index.json`에 없던 36,720개 파일도 사용 가능
- → **위 전부에 단독 F1 검사 선행** (슬라이드 19)

**트랙 4. 배터리 이상 탐지**
- 대상: NPY 수치 행렬 (셀 96/98개 전압·편차), 3클래스 분류

- 셀전압 결함: 개별 셀 min/max, 임계 초과 셀 수 / 셀편차 결함: 셀 간 표준편차, 최대–최소 편차
- **참조데이터 배터리 220,320파일은 이미 확보 완료** (`battery_all.parquet`, 4.72M행)
