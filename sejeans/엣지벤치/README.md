# 엣지벤치 — 라즈베리파이4 추론속도 측정

MiniRocket + LogisticRegression 모델을 파이4에서 돌려 **청크 1개당 지연시간**을 잰다.

| 파일 | 역할 |
|---|---|
| `bench_latency.py` | 벤치마크 본체. 단독 실행(프로젝트 패키지 의존 없음) |
| `requirements-pi.txt` | 파이용 고정 버전 |
| `run_all.sh` | 1/2/4 코어 × 배치 1/8/32 전체 스윕 |

---

## 0. 전제 — 반드시 64비트 OS

```bash
uname -m      # aarch64 여야 한다
```

`armv7l` 이 나오면 **여기서 멈춘다.** numba/llvmlite 는 32비트 ARM 휠을 제공하지
않아서 LLVM 을 소스빌드해야 하고, 파이4에서 몇 시간 걸린 뒤에도 실패하기 쉽다.
Raspberry Pi Imager 로 *Raspberry Pi OS (64-bit) Bookworm* 을 다시 굽는 게 빠르다.
Bookworm 의 기본 파이썬이 3.11 이라 학습 PC(3.11.0)와도 맞는다.

측정 신뢰도를 위해 같이 확인할 것:

```bash
vcgencmd get_throttled     # 0x0 이 아니면 전압강하/과열 이력 있음
vcgencmd measure_temp      # 유휴 시 60℃ 넘으면 방열 대책 먼저
```

정품 5V/3A 전원 + 방열판(가능하면 팬) 없이 재면 스로틀 때문에 실제보다 느린
숫자가 나온다. 이 스크립트는 시작/종료 시점의 온도·스로틀 플래그를 결과 JSON 에
같이 남기므로, 발표 때 "스로틀 없음"을 근거로 댈 수 있다.

## 1. 파이 환경 구성

```bash
sudo apt update && sudo apt install -y python3-venv python3-dev libatlas-base-dev
python3 -m venv ~/bench-venv
source ~/bench-venv/bin/activate
pip install --upgrade pip
pip install -r requirements-pi.txt          # 5~15분 (aarch64 휠 받아옴)
```

Bookworm 은 PEP 668 로 시스템 파이썬에 직접 설치를 막는다. venv 는 선택이 아니다.

## 2. 파일 옮기기

`models/` 는 이미 채워져 있다 (아래 "무엇을 재는가" 참고). 폴더째 옮기면 된다.

```powershell
# PC 에서 — 파이 IP 가 192.168.0.20 이라고 가정
scp -r 엣지벤치 pi@192.168.0.20:~/bench
```

한글 경로가 부담스러우면 파이 쪽 폴더명은 `~/bench` 처럼 영문으로 받는 게 편하다.

### 무엇을 재는가

`models/` 의 6개는 두 축을 각각 훑도록 골라둔 것이다.

| 파일 | 채널 | 커널 | macro-F1 |
|---|---|---|---|
| `model_registry_fuse_rpm_ext_ord_k1250.joblib` | 87 | 1,176 | 0.959 |
| `model_registry_fuse_rpm_ext_ord_k2500.joblib` | 87 | 2,436 | 0.969 |
| `model_registry_fuse_rpm_ext_ord_k5000.joblib` | 87 | 4,956 | 0.971 |
| `model_registry_ord_B_87ch_k10000.joblib` | 87 | 9,996 | 0.973 |
| `model_registry_48ch_k10000.joblib` | 48 | 9,996 | 0.965 |
| `model_registry_15ch_k10000.joblib` | 15 | 9,996 | 0.881 |

앞 4개 = **커널 수 축**(채널 87 고정), 뒤 3개 = **채널 수 축**(커널 10,000 고정).
뒤 둘은 알아보기 쉽게 이름을 바꿔 복사한 것으로, 원본은 각각
`본격/모델/모델/model_registry_fuse_rpm{,_ext_no_band_ratio_7}.joblib` 이다.

registry 하나에 차종 3개(IONIQ/KONA/NIRO)가 들어 있지만 셋은 채널·커널이 같아
지연시간이 거의 동일하다(학습 PC 측정 23.46 / 23.59 / 23.89 ms). 그래서 기본은
registry 당 1슬롯만 잰다. 전부 재려면 `--slots 0`.

## 3. 측정

```bash
cd ~/bench
source ~/bench-venv/bin/activate
bash run_all.sh ./models
```

모델 6개 × 스레드 3종 × 배치 3종. 파이4에서 **1시간 안팎** 예상.

단발로 돌릴 때:

```bash
python bench_latency.py --models ./models --threads 4 --batch 1 --reps 30
```

결과는 `bench_pi4_t{1,2,4}_b{1,8,32}.json` + 콘솔 마크다운 표로 나온다.

중간에 수십 초씩 멈춘 것처럼 보이는 건 numba JIT 컴파일이다. 프로세스가 바뀔 때마다
다시 컴파일하므로 정상이다.

## 4. 숫자 읽는 법

- **`per_chunk_ms_p50` 이 핵심 지표다.** 청크 1개 = 2,000 스텝. 이게 청크 하나가
  쌓이는 실시간 주기보다 작아야 실시간 추론이 성립한다.
- **평균이 아니라 p95/p99 로 판단한다.** 실시간 시스템의 합격 기준은 평균이 아니라
  꼬리지연이 마감을 넘기느냐다.
- **`jit_warmup_s` 는 버리는 숫자가 아니다.** MiniRocket 은 numba JIT 이라 첫 호출에
  커널을 컴파일한다(파이4에서 수십 초 가능). 실차에서는 "시동 후 첫 진단까지의
  대기시간"이 되므로 별도 항목으로 보고할 것. 지연시간 통계에는 포함하지 않는다
  (warmup 이후만 잰다).
- **`minirocket_ms_p50` vs `clf_ms_p50`.** MiniRocket 이 전체의 98%, LR 은 0.5% 다.
  경량화 대상은 분류기가 아니다.
- **코어 수.** 배치 1 에서는 스레드 분할 오버헤드가 커서 1코어가 더 빠를 수 있다.
  그래서 1/2/4 를 다 재는 것이다. 결론은 측정으로 정한다.

## PC 기준선 (검증 완료, 2026-08-23)

학습 PC 와 같은 버전(sklearn 1.7.2 / sktime 1.1.0 / numba 0.62.1)으로
`models/` 의 실제 모델 6개를 **1스레드**로 잰 값이다. 파이 결과를 이 표 옆에
두면 "엣지에서 몇 배 느려지는가" 가 바로 나온다.

| 구성 | 채널 | 커널 | macro-F1 | p50 |
|---|---|---|---|---|
| `15ch_k10000` | 15 | 9,996 | 0.881 | 34.5 ms |
| `ord_k1250` | 87 | 1,176 | 0.959 | 50.9 ms |
| `48ch_k10000` | 48 | 9,996 | 0.965 | 59.7 ms |
| `ord_k2500` | 87 | 2,436 | 0.969 | 99.1 ms |
| `ord_k5000` | 87 | 4,956 | 0.971 | 100.2 ms |
| `ord_B_87ch_k10000` | 87 | 9,996 | 0.973 | 108.6 ms |

### 커널 수를 줄여도 지연시간은 그만큼 안 준다

직관과 다르다. 커널 10,000 -> 5,000 은 **8% 밖에 안 빨라진다.**

MiniRocket 의 연산량은 feature 수가 아니라 **(채널조합 × dilation) 쌍의 개수**에
비례한다. 컨볼루션을 한 번 돌린 뒤 bias 를 여러 개 얹어 PPV 만 세는 구조라,
feature 를 늘리는 건 대부분 값싼 카운팅이 늘어나는 것이다.
게다가 dilation 개수에는 상한(`max_dilations_per_kernel=32`)이 있다.

실제 적재된 모델의 `mr.parameters[0]` 길이(= 채널·dilation 쌍):

| 커널 | 쌍 개수 | 상대 | 측정 p50 상대 |
|---|---|---|---|
| 1,176 | 1,092 | 1.00 | 1.00 |
| 2,436 | 2,016 | 1.85 | 1.94 |
| 4,956 | 2,184 | 2.00 | 1.96 |
| 9,996 | 2,184 | 2.00 | 2.13 |

k5000 과 k10000 은 dilation 구조가 **완전히 동일**하다(둘 다 2,184). 상한에 걸려
포화된 것이다. 그래서 두 모델의 지연시간이 사실상 같다.

**결론**: 커널 축소로 의미 있는 속도 이득을 보려면 2,500 아래로 내려가야 한다.
k5000 은 k2500 과 같은 속도에 F1 이 더 높으니(0.971 vs 0.969) k2500 을 쓸 이유가 없다.

### 정확도-속도 프론티어

위 표에서 살아남는 선택지는 넷이다:

| 선택 | F1 | p50 | 언제 |
|---|---|---|---|
| 87ch k10000 | 0.973 | 108.6 ms | 속도 여유 있을 때 |
| 87ch k5000 | 0.971 | 100.2 ms | 거의 공짜로 8% 절감 |
| **48ch k10000** | 0.965 | 59.7 ms | **속도 대비 정확도가 가장 좋다** |
| 87ch k1250 | 0.959 | 50.9 ms | 최속. F1 0.014 를 더 내준다 |

주목할 점: `48ch k10000` 이 `87ch k1250` 과 지연시간이 비슷한데(60 vs 51 ms)
F1 은 더 높다(0.965 vs 0.959). **커널을 줄이는 것보다 채널을 줄이는 쪽이 이 구간에서
더 이득**이라는 뜻이다. 파이에서도 이 순위가 유지되는지가 이번 측정의 핵심 질문이다.
